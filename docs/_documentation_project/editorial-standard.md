# Editorial Standard

Status: Active

This standard governs public Ordo prose.

## Reader Promise

The reader should leave with less confusion and more trust.

A good Ordo doc tells the reader:

- what Ordo is
- why it matters
- what is real today
- what is still being built
- how to participate
- where to go next

## Voice

Ordo should sound like a builder with a working system and a real civic thesis.

The voice is:

- clear
- alive
- grounded
- exact
- ambitious
- humane
- allergic to empty hype

The voice is not:

- generic SaaS marketing
- academic over-explanation
- investor-deck fog
- mystical AI language
- internal implementation diary
- a list of every capability in the codebase

## Keith's Register

Use the user's natural register as the reference point:

- fast velocity, but not sloppy velocity
- software manufacturing, not prompt tricks
- public value, not private spectacle
- AGPL and community as an anti-enshittification stance
- appliance-first, ownable, local-first where practical
- human trust and follow-through as the scarce resource
- AI consultants, product engineers, and QA volunteers as real participants

The prose can be inspirational, but it must earn that feeling through concrete
facts.

## Page-Level Test

Every public page must answer:

1. What is Ordo?
2. Why does it matter now?
3. What is real today?
4. What is being shaped next?
5. What should the reader do?

If a page cannot answer those questions, narrow its scope.

## Compression Rules

- Keep the first screen light.
- Move deep architecture into linked docs.
- Use lists only when scanning helps.
- Cut repeated claims.
- Replace abstract labels with concrete nouns.
- Prefer `Ordo runs...` over `Ordo is designed to facilitate...`.
- Prefer `QA reports become work orders` over `an integrated feedback process is
  planned` when the code supports the claim.

## Claim Labels

Use these labels mentally while drafting, and explicitly when ambiguity matters:

- **Implemented**: supported by code, tests, or current docs.
- **Active refactor**: in current plans/phases and partially implemented.
- **Alpha track**: intended for the July 31, 2026 alpha but not done.
- **Vision**: strategic direction, not a current product claim.

Do not blur these categories.

## Prose QA Checklist

Before closeout, read every public page aloud enough to catch drag.

Check for:

- one real opening claim
- no unsupported superlatives
- no hidden feature overclaims
- no unexplained acronyms in first-contact copy
- no paragraphs that exist only to sound important
- no repeated lists of the same capabilities
- one clear next step for readers
- links to deeper proof where serious builders need it

## Banned Defaults

Avoid these unless quoting an existing term or naming a precise system:

- revolutionary
- seamless
- cutting-edge
- unlock
- empower
- leverage, unless talking about the process thesis directly
- world-class, unless a concrete external standard is named
- AI-powered, unless the sentence explains what the AI actually does
