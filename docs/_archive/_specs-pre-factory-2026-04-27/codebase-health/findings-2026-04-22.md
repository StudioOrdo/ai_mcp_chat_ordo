# Codebase Health Findings — Post Phase 1

Status: Active
Date: 2026-04-22
Author: GitHub Copilot (observations from Phase 1 implementation)
Scope: Notes for post-sprint remediation. No work implied during current refactor package.

## Purpose

Capture technical-debt observations gathered while implementing Phase 1 of
the beginner-solopreneur-refactor. Each finding is paired with a proposed
remediation sized for a dedicated follow-up sprint. Nothing here blocks the
current phase package.

## Findings

### F1. TypeScript `--noEmit` baseline of 51 pre-existing errors

**Observation**

`npx tsc --noEmit` exits non-zero with a stable ~51-line error baseline,
spanning roughly 10+ files across unrelated subsystems. Because the baseline
is treated as known, type regressions inside those files are invisible.

Affected files (grouped):

- Config: `next.config.ts` (eslint key no longer in `NextConfig`).
- Capability catalog tests: `src/core/capability-catalog/runtime-tool-binding.test.ts`
  (mock shape drift vs. `UserFileRepository`, `UserFileType`, and
  conversation record types).
- Use-case tests: `src/core/use-cases/ConversationInteractor.test.ts`
  (mock missing `listForUser`, `getUserStorageSummary`, `listForAdmin`,
  `countForAdmin`, and more).
- Job runtime: `src/lib/jobs/compose-media-deferred-job.test.ts`
  (`beforeEach` not imported; `conversationId` not in `ChatMessage`),
  `src/lib/jobs/deferred-job-runtime.test.ts`
  (`id` not in `Pick<MediaCompositionPlan, ...>`),
  `src/lib/jobs/job-capability-registry.ts` (generic variance mismatch
  on `CatalogJobCapabilityName`).
- Media pipeline: `src/lib/media/browser-runtime/ffmpeg-browser-executor.test.ts`
  (possibly-undefined `result.envelope`),
  `src/lib/media/server/compose-media-mermaid-renderer.ts` (`type` not in
  `WorkerOptions`),
  `src/lib/media/server/compose-media-plan-materialization.ts` and its test
  (incompatible `MaterializedStoredAssets` / `MediaAssetSource`; `Error`
  vs `string` in error-payload arg),
  `src/lib/media/server/media-worker-client.test.ts` (duplicate
  `MediaWorkerClient` identifier),
  `src/lib/media/server/media-worker-http.test.ts` (missing
  `subtitlePolicy` / `outputFormat` on `MediaCompositionPlan`).
- Playwright: `tests/browser-ui/media-compose-planner-eval.spec.ts`
  (`null` → `PersistedPlanSnapshot` mistake).
- Deferred worker: `tests/deferred-job-worker.test.ts`
  (`aborted` on `never`).

**Impact**

- Type-checking is effectively not a regression gate.
- New work can silently break these files further.
- CI signal is binary "expected-to-fail"; meaningful drift is undetectable
  without a diff of full tsc output.

**Recommended remediation (T-shirt: L)**

1. Freeze the current baseline with a structured snapshot: run
   `npx tsc --noEmit` and commit the deduped file list to
   `docs/_specs/codebase-health/tsc-baseline.txt`.
2. Add a CI step `scripts/check-tsc-baseline.ts` that fails only when a file
   _not_ on the baseline produces an error, or when the total count grows.
3. Schedule per-subsystem cleanup tickets grouped by the above categories.
   Media pipeline and capability-catalog tests are the two largest groups
   and should each be their own ticket.
4. After each group is green, delete its entries from the baseline and
   tighten the CI check until the baseline is empty.
5. Once empty, flip CI to require `tsc --noEmit` exit 0.

### F2. Three modules permanently flagged "out of scope"

**Observation**

`deferred-job-worker.ts`, `runtime-tool-binding.ts`, and
`search-my-conversations.tool.ts` are explicitly marked as untouchable in
every phase of the current refactor. This is the strongest code smell in
the repository: nobody wants to pay their refactor cost.

- `src/lib/jobs/deferred-job-worker.ts`: the central worker loop for the
  deferred-job pipeline.
- `src/core/capability-catalog/runtime-tool-binding.ts`: the runtime binder
  between capability catalog entries and tool execution.
- `src/core/use-cases/tools/search-my-conversations.tool.ts`: the
  conversation-memory retrieval tool.

All three are high-value, frequently-reached modules whose coupling has
accumulated.

**Impact**

- Features that touch conversation memory, tool runtime, or deferred jobs
  have to work around them.
- New envelopes, new tool families, and new capability kinds end up with
  ad-hoc passthrough paths (see F4) because the primary path is frozen.
- The "hotspot" label risks becoming permanent.

**Recommended remediation (T-shirt: XL per module)**

Dedicated hotspot-reduction sprint after Phase 6:

1. Per module, produce a dependency map (what calls it, what it calls,
   shared state, hidden contracts).
2. Write a "characterization" test suite capturing current behavior before
   touching anything.
3. Extract stable ports/adapters:
   - For `deferred-job-worker.ts`: split scheduler, executor, and failure
     policy into three files with a thin orchestrator.
   - For `runtime-tool-binding.ts`: isolate catalog lookup, context
     construction, and dispatch. Most drift lives in context construction.
   - For `search-my-conversations.tool.ts`: move retrieval policy out of
     the tool body into a `ConversationRetrievalInteractor`.
4. Only once extracted and tested, allow feature work to flow through the
   new seams.

### F3. Regression sweep is narrower than the surface area

**Observation**

Phase 1 QA relied on 124 tests in the focused sweep (access, library,
corpus, presentation, error-standardization, public-content-routes). Media
pipeline, deferred jobs, admin, proxy, middleware, referral, and
integration suites were not in the primary gate — partly because of F1
and F2.

**Impact**

- High-risk surfaces (media, jobs, admin) regress without being noticed
  until browser-UI or integration tests catch them later.
- Per-phase QA gate is optimistic.

**Recommended remediation (T-shirt: M)**

1. Define a canonical "phase QA" vitest pattern in `package.json`:
   `test:phase-gate` that runs everything except known-broken suites.
2. Resolve F1 so broken suites shrink to zero.
3. Promote `test:phase-gate` into every phase's evidence file as the
   mandatory regression gate.

### F4. Two parallel capability stores

**Observation**

- `CAPABILITY_CATALOG` (server) and `CLIENT_CAPABILITY_CATALOG` (client)
  are the official registry.
- Newer descriptors (e.g. `LIFECYCLE_EVENT_DESCRIPTOR` from Phase 1) live
  outside the catalog and route via `ChatPresenter.lifecycle` passthrough.

Both patterns are correct for their current use, but the split is
undocumented and the choice of which path to take is ad-hoc.

**Impact**

- Phase 2 lifecycle-coach cards, Phase 4 assistant cards, and any future
  system card will each face the same "catalog vs passthrough" decision
  without guidance.
- Risk of ending up with three or four parallel stores.

**Recommended remediation (T-shirt: M)**

1. Write `docs/_specs/codebase-health/capability-descriptor-placement.md`
   that states the decision rule (catalog = LLM-tool-invocable;
   passthrough = system-authored envelopes on stored messages).
2. Add a test asserting every `CAPABILITY_CATALOG` entry round-trips
   through `CLIENT_CAPABILITY_CATALOG` and every `cardKind` has a resolver.
3. Decide whether lifecycle stays passthrough or registers in the catalog
   when Phase 2 adds coach envelopes. Document the decision in the
   evidence file for the phase that introduces additional system kinds.

### F5. `user_preferences` is becoming a general-purpose KV

**Observation**

`UserPreferencesDataMapper.ALLOWED_KEYS` now holds a mix of:

- User-facing preferences writable via `set_preference`
  (`SUPPORTED_PREFERENCE_KEYS` subset).
- System-owned state writable only server-side: `account_tier`,
  `pending_lifecycle_events`.

The security split between the two lists is correct (see Phase 1 evidence)
but the convention is implicit, not enforced by types.

**Impact**

- Easy for a future contributor to add a key to `ALLOWED_KEYS` assuming
  users can write it, without realizing the security boundary runs through
  `SUPPORTED_PREFERENCE_KEYS`.
- Value shapes (`account_tier` is a short string; `pending_lifecycle_events`
  is a JSON-serialized array cap 4000 chars) are enforced only by
  `MAX_VALUE_LENGTHS` + local parse logic.

**Recommended remediation (T-shirt: M)**

1. Split `ALLOWED_KEYS` into two typed groups in
   `UserPreferencesDataMapper.ts`:
   `USER_WRITABLE_KEYS` and `SYSTEM_WRITABLE_KEYS`.
2. Expose separate `put` methods: `putUserWritable(userId, key, value)`
   (called from `set_preference`) and `putSystemWritable(userId, key,
   value)` (called from admin/server paths).
3. Add a test asserting `SUPPORTED_PREFERENCE_KEYS ⊆ USER_WRITABLE_KEYS`
   and disjoint from `SYSTEM_WRITABLE_KEYS`.
4. Long term, consider migrating system keys out of `user_preferences`
   into a dedicated `user_system_state` table if the list grows past 5
   entries.

### F6. Test-mock drift vs. production repository shapes

**Observation**

Several tsc errors in F1 are mock objects that have fallen behind the
repository interface they stub (`UserFileRepository` is the most common
offender, missing `listForUser`, `getUserStorageSummary`, `listForAdmin`,
`countForAdmin`). This is structural, not incidental.

**Impact**

- Every interface change on a repository requires hunting down and
  updating N bespoke mocks.
- Mocks that compile today will break silently after the F1 cleanup.

**Recommended remediation (T-shirt: M)**

1. Add `src/testing/mocks/repositories/` with one `create*Mock()` factory
   per port interface.
2. Each factory returns a fully-shaped mock with `vi.fn()` default
   implementations and a typed override param.
3. Migrate failing test mocks to the factories incrementally while
   resolving F1.

### F7. Structured notebook for system-owned envelopes is undocumented

**Observation**

Phase 1 showed that a system-authored envelope (lifecycle) is persisted by:

1. Writing it into `user_preferences(key=pending_lifecycle_events)` as a
   JSON array.
2. (Future Phase 2) Draining into a chat message with
   `metadata.lifecycle` set.
3. `ChatPresenter.present()` forwarding metadata.lifecycle to the UI.
4. `MessageList` rendering `<LifecycleCard>` when `role === "system" &&
   lifecycle`.

The exact drain/hydrate contract is not yet written because Phase 2 hasn't
landed. Without a spec, Phase 2 has freedom to pick any shape.

**Impact**

- Risk of Phase 2 diverging from the envelope pattern and inventing a new
  shape for coach cards.

**Recommended remediation (T-shirt: S)**

1. Before Phase 2 implementation, write
   `docs/_specs/beginner-solopreneur-refactor/system-envelope-contract.md`
   documenting:
   - Server → pending queue → chat message metadata → presenter →
     renderer flow.
   - Rule: any system envelope travels as
     `CapabilityResultEnvelope<TPayload>` with `family: "system"` and a
     registered `cardKind`.
   - Rule: `ChatMessage.metadata.<kind>?` passthrough on `role: "system"`
     messages; one key per cardKind.

This is also a Phase 2 prerequisite, not standalone remediation.

### F8. Error envelope and tsc are weak signals right now

**Observation**

- eslint is green on touched files (good).
- Vitest focused sweep passes (good).
- tsc is broken (F1).
- No single `npm run ci` equivalent was runnable during Phase 1 QA; I ran
  eslint, vitest, and tsc as three separate commands, each with separate
  interpretation.

**Impact**

- Local QA is not push-button.
- Phase evidence files are manually composed from three command logs.

**Recommended remediation (T-shirt: S)**

1. Add `npm run verify` = eslint + vitest (phase gate) + tsc (once F1 is
   clean).
2. Require `npm run verify` output attached to each phase evidence file.
3. Cache tsc and vitest output via TurboRepo or a simple script to keep
   wall-clock under 60s.

## Priority ordering for post-sprint remediation

1. **F1 + F6 together** — essential. tsc baseline + mock factories unblock
   everything else.
2. **F3 + F8** — short effort, high leverage for phase-QA confidence.
3. **F4** — one afternoon of documentation; prevents future divergence.
4. **F5** — needed before `user_preferences` gains its next system key.
5. **F7** — write it _before_ Phase 2 starts implementing.
6. **F2** — XL, multi-module. Tackle after the current 6-phase refactor
   closes out.

## Non-findings (things that worked well, for the record)

- Clean architecture layering held under new cross-cutting work
  (`UserTier` threaded through 7+ layers with zero backward references).
- Typed `CapabilityResultEnvelope<TPayload>` + descriptor + shell trio
  made the new lifecycle surface a copy-and-fill exercise.
- `ChatPresenter` as a metadata→UI seam made lifecycle rendering
  non-invasive.
- Memory/spec discipline (evidence files, repo memory, tracker) made
  Phase 1 resumable across sessions.
- Security-pin enforcement at the test layer (set_preference test) is a
  pattern worth keeping.
