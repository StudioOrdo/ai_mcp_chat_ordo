# Specification: Realtime Broker & Human Handoff

**Audience:** Implementation AI Agent
**Context:** This specification defines the replacement of Node.js Server-Sent Events (SSE) polling with a high-performance Rust Pub/Sub broker to support real-time multi-user chat and instant UI updates.

## 1. The Problem with SSE Polling
Currently, `job-event-stream.ts` uses a `while` loop to repeatedly query SQLite every 500ms. This exhausts the Node.js event loop and SQLite locks as concurrent users scale.

## 2. The IPC Bridge (Node.js -> Rust)
We must move from a "Pull" architecture to a "Push" architecture.
*   **Unix Domain Sockets (UDS):** Node.js will push events to the Rust `ordo-daemon`.
*   **Fire-and-Forget:** When an LLM token is generated by Anthropic, or a job status updates in the DB, Node.js fires a highly-efficient, non-blocking JSON payload over UDS to the Rust Broker.

## 3. WebSockets & Multi-User Chat
The UX invariant states: *"Chat is the operating interface."* To support advanced workflows like transferring a conversation from the AI to a Human Operator, we must migrate from unidirectional SSE to bidirectional WebSockets.
*   **The Connection:** React clients connect to the Rust Broker via WebSocket, subscribing to a specific `conversationId`.
*   **Bidirectional Events:** WebSockets allow the browser to push "User is typing..." indicators directly to the Rust Broker, which instantly broadcasts them to all clients in that channel (including the Operator's browser).
*   **Routing Logic:**
    *   If the conversation lane = `bot`: The Rust Broker forwards the incoming user message to the Node.js API to trigger LLM inference.
    *   If the conversation lane = `human`: The Rust Broker simply broadcasts the message to the other connected clients. No LLM inference is triggered.

## 4. Instant UI Governance
When a background task (like a Backup or Media Workflow) completes natively in Rust, it does not need to cross the IPC bridge to Node.js. It simply publishes a `governance_update` event directly to the internal Tokio broadcast channel. The Broker pushes this via WebSocket to the React app, immediately triggering a UI cache invalidation (e.g., SWR mutate) without the user refreshing the page.
